# Architecture

## System Overview

The booru prototype is an event-sourced image gallery built around three persistent concerns:

- Git LFS stores immutable image bytes by SHA-256 OID.
- A library Git repository stores small pointer files and append-only NDJSON metadata events.
- Derived JSON indexes materialize the gallery state needed by HTTP handlers.

The HTTP server combines these concerns for a local prototype. Ingest uploads image bytes to the LFS server, writes repository files, and commits pointer/event changes. Reads use the derived image-state index for gallery HTML and proxy image bytes from the LFS server by OID.

## Architectural Goals Visible in Code

The code favors a Git-native, rebuildable data model over a mutable database service:

- Metadata history is append-only NDJSON.
- Derived indexes are disposable JSON files produced by replay.
- Image content is content-addressed outside the repository through Git LFS.
- Library repositories remain ordinary Git repositories with `.gitattributes`, `.lfsconfig`, and committed pointer/event files.
- Storage boundaries are simple TypeScript interfaces rather than framework-level abstractions.

## Source of Truth

The authoritative metadata model is the event log under `events/`. Events support `add`, `tag_add`, `tag_remove`, and `delete` operations. Replaying those events produces two materialized views:

- `image_state.json`: image ID to image metadata.
- `tag_index.json`: tag to image ID list.

Image bytes are authoritative in the Git LFS object store. The repository stores pointer files that identify the LFS objects, not hydrated image content.

`event_cursor` is replay bookkeeping. It records the last processed event position, but it is not metadata truth and can be regenerated by replaying from the beginning.

## Git and Git LFS Responsibilities

Git is used for library history and durability of small files:

- pointer files under `images/`
- NDJSON event shards under `events/`
- repository configuration and placeholders

Git LFS is used for image bytes:

- `handleIngest` computes a SHA-256 OID from uploaded bytes.
- `PutObjectMeta` registers object metadata.
- `PutObjectContent` uploads bytes.
- `handleImage` retrieves bytes with `GetObjectContent`.

The library `.gitattributes` routes image extensions through LFS filters. `.lfsconfig` points at `http://localhost:8080` and excludes automatic fetches. `Init` clones the template with smudge skipped, appends local skip-smudge config, and adds a sample upstream remote.

## Component Boundaries

### HTTP boundary

`server.ts` owns process startup, hardcoded runtime configuration, route selection, and the initial index rebuild check. It does not parse events or write indexes directly.

`src/handlers.ts` owns request-specific behavior:

- Gallery rendering from `DerivedIndexStore` or direct JSON reads in the legacy handler.
- Multipart ingest validation, OID calculation, LFS upload, pointer/event writes, and Git commit.
- Image proxying to the LFS server.

### Event-log boundary

`EventLog` is append-oriented. `EventLogReader` is separate so append consumers do not need file-reading semantics. `NdjsonEventLog` is the file-backed implementation and encodes shard scanning, cursor seeking, line decoding, and JSON parsing.

Ingest does not cross this abstraction; it writes a hardcoded event shard directly. Replay uses the abstraction through `processEventsNew`.

### Derived-index boundary

`DerivedIndexStore` is the storage contract for replay and gallery reads. `JsonFileIndexStore` implements the contract with JSON files and a mutex.

The indexer calls `store.applyEvent` instead of writing files itself. HTTP gallery rendering calls `store.listImages`. Ingest bypasses the store for dedupe and ID allocation, which is an important boundary leak.

### LFS boundary

`src/lfs/api.ts` is a thin fetch wrapper. It constructs URLs from `Connection`, sets Git LFS media-type and authorization headers, and returns raw `Response` objects. It does not hide upstream status codes or response bodies behind a domain-specific result type.

### Git boundary

Git operations are localized to `Init` and `internalIngest`. `Init` handles clone/setup. `internalIngest` stages and commits the pointer file plus the event shard after LFS upload and local file writes.

## Data Flow

### Ingest flow

```text
client multipart POST /ingest
  -> request boundary validates image field and tags JSON
  -> content boundary computes SHA-256 OID
  -> derived-index read checks for duplicate OID and next numeric ID
  -> LFS boundary registers metadata and uploads bytes
  -> filesystem writes pointer file and NDJSON event
  -> Git boundary stages and commits both files
  -> HTTP response returns { id }
```

This path is synchronous. The client waits for LFS and Git operations before receiving a success response. A failure before file writes leaves no pointer/event files. A failure during Git staging or commit can leave local files written without a successful commit.

### Image-serving flow

```text
gallery request
  -> DerivedIndexStore.listImages()
  -> HTML includes /image/{oid}

image request
  -> route extracts OID
  -> LFS client fetches object content
  -> upstream response is returned
```

The booru does not maintain a blob cache. Image bytes are fetched from the LFS server for each image request.

### Replay flow

```text
startup or indexer
  -> choose JSON store and event log
  -> read cursor from store cache
  -> read sorted NDJSON shards from events/
  -> parse event lines
  -> apply each event to image and tag state
  -> write image_state.json, tag_index.json, and event_cursor
```

The pure event reducer lives in `applyEvent`. It mutates in-memory state only. File persistence and cursor advancement belong to the store.

## Persistence Model

A library repository contains the canonical small-file history and the derived local state:

```text
events/*.ndjson       canonical metadata events
images/*              Git LFS pointer files
event_cursor          replay checkpoint
index/image_state.json derived image state
index/tag_index.json   derived tag index
```

The `index/` directory is ignored by the library repository except for `.gitkeep`, reflecting its role as local derived state. Event shards and pointer files are committed by ingest. `event_cursor` is written beside the index files as replay bookkeeping.

JSON index writes use a temp-file-and-rename pattern per file. The store writes multiple files in sequence, so the group of files is not atomic as a unit.

## Invariants and Assumptions

- Event replay order is shard-name sort order, then line order within each shard.
- Image IDs are strings in derived indexes, even when ingest events carry numeric IDs.
- The ingest path uses sequential numeric IDs based on the maximum ID in `image_state.json`.
- OIDs are SHA-256 hashes of uploaded bytes.
- Pointer file content is derived from OID and byte size using the Git LFS pointer format.
- `add` events carry full image state needed to materialize the image index.
- Tag indexes are derived from image state and tag events; they are not canonical.
- Startup treats missing derived index files as a rebuild trigger.
- The hardcoded server configuration assumes an LFS server at `localhost:8080` and a local library at `libraries/new`.

## Trust and Failure Boundaries

### Request input

`handleIngest` validates that the multipart request includes an `image` file and that `tags` parses as a JSON array. Other metadata fields are accepted as strings or parsed integers with fallback values. Gallery output interpolates names and tags into HTML without escaping, so stored metadata is trusted by the renderer.

### LFS server

The LFS client returns fetch responses directly. `internalIngest` checks `ok` for metadata registration and content upload before writing local files. `handleImage` returns the upstream content response without additional validation.

### Filesystem and event parsing

Event replay parses each NDJSON line as JSON and lets unexpected parse or filesystem errors fail the replay. Missing `events/` is treated as an empty event set by `NdjsonEventLog.readEvents` and by the older `processEvents` implementation.

### Derived index consistency

A mutex serializes JSON-store operations within the process. It does not provide cross-process locking. A crash or external mutation between writing `image_state.json`, `tag_index.json`, and `event_cursor` can leave the derived files inconsistent. Because metadata truth is the event log, safe recovery is to rebuild derived files from events.

### Cursor semantics

`JsonFileIndexStore` keeps the cursor in memory after a save, but `getCursor()` does not load `event_cursor` from disk. A fresh store instance therefore starts replay from a null cursor unless another code path has populated the cache. This makes the persisted cursor less authoritative than its file layout suggests.

### Git operations

Git add and commit errors are converted into JSON HTTP errors inside `internalIngest`. The LFS upload and local file writes happen before these Git operations. There is no rollback for uploaded LFS objects or local pointer/event writes after a Git failure.

## Design Tradeoffs

### Event log over mutable records

Append-only events make metadata history auditable and derived indexes rebuildable. The tradeoff is that read-serving state depends on replay correctness and index freshness.

### JSON files over a database

JSON indexes are easy to inspect and require no service dependency. They also require whole-file read/modify/write cycles and coarse in-process locking, which limits write concurrency and large-index performance.

### Synchronous Git commit in ingest

Committing during the request path keeps repository history aligned with acknowledged ingests. It also couples request latency and availability to Git process execution and repository state.

### Content-addressed blobs with sequential image IDs

LFS OIDs provide deduplication and immutable content addressing. Sequential IDs provide short booru-style storage keys and display identifiers. The cost is that ID allocation depends on a fresh and complete image-state index.

### Thin LFS client

Returning raw `Response` objects keeps the LFS boundary simple and transparent. Callers must inspect status codes and content themselves, and higher-level retry or rollback policy is not centralized.

### Partial abstraction adoption

The code contains newer `EventLog` and `DerivedIndexStore` boundaries, but ingest still writes events and reads indexes directly. Safe changes need to account for both paths until handlers consistently use the abstractions.
